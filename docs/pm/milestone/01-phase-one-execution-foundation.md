# 第一阶段：可持续执行

## 迭代定位

将产品从“依赖一次连接完成回答的代码聊天”迭代为“能够持续运行、保存过程并恢复的代码任务”。

这一阶段的产品形态是**只读 Coding Harness**：用户选择工作区、创建任务并观察执行过程；系统可以读取代码、分析仓库和生成建议，但不修改文件，也不执行未经隔离的命令。

## 要做的事情

### 建立任务空间

- 用户可以选择或创建 Workspace。
- 用户可以围绕一个持续目标创建 Thread，并在其中多轮协作。
- 每次用户输入形成独立 Turn，明确展示排队、运行、完成、失败、中断等状态。
- Agent 的消息、模型调用和工具动作以 Item 形式展示，不再混在一条不可恢复的流中。

### 让执行脱离页面连接

- 创建 Turn 后立即返回任务标识，由 Harness 独立执行。
- 页面关闭或网络断开不会取消任务。
- 用户重新进入任务后，可以补齐离线期间产生的事件。
- 用户可以主动中断任务；系统不会把断线误判为中断。

### 保存稳定执行状态

- 在模型调用前后等稳定边界保存 Checkpoint。
- 服务异常后将未完成任务标记为可识别的中断状态。
- 用户可以从最近稳定点继续，而不是从头重复整个任务。
- 同一个 Thread 同时只运行一个 Turn，避免上下文和结果相互覆盖。

### 建立执行边界

- 文件读取只能发生在用户选定的工作区内。
- 敏感文件和工作区外路径默认不可读取。
- 命令能力只有在可信执行隔离可用时才开放；否则保持关闭。
- 模型只负责提出下一步，不能直接修改任务状态或绕过 Harness 执行动作。

### 展示可理解的过程

- 执行流展示当前阶段、已读取内容、工具结果和错误原因。
- 大段输出使用摘要和按需查看，避免淹没主要任务过程。
- 刷新页面后，任务状态和事件顺序保持一致。
- 最终结果明确区分已完成、部分完成、失败和被中断。

## 用户使用流程

```text
选择 Workspace
  -> 创建 Thread
  -> 输入代码任务
  -> 查看持续执行过程
  -> 断开后重新进入
  -> 查看完整结果
  -> 继续追问或主动恢复
```

## 交付形态

- Workspace 和 Thread 列表。
- 可持续运行的 Turn。
- 可重放的执行事件流。
- 中断与主动恢复入口。
- 只读代码分析能力。
- 明确的执行限制和错误状态。

## 完成标准

- 页面断开后，任务仍能完成并保存全部过程。
- 重新连接后，事件连续、顺序正确且不重复。
- 异常退出不会把未完成任务显示为成功。
- 用户可以从稳定点恢复被中断的任务。
- 同一任务不会被重复执行。
- 工作区外文件和未授权命令无法被访问。

## 本阶段不做

- 文件修改和代码补丁。
- 工具审批和永久授权。
- Diff、ChangeSet 和验证报告。
- 自动提交、推送或部署。
- 多 Agent、云端执行和 IDE 插件。

## 下一迭代形态

在可持续执行稳定后，产品进入“安全交付闭环”：Agent 不仅能理解代码，还能在明确权限下修改和验证代码，并把所有变化作为可审查结果交付给用户。
