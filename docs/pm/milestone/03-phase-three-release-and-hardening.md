# 第三阶段：可配置内测产品

## 迭代定位

将产品从“单一入口、单一模型的安全 Coding Harness”迭代为“可配置、可度量、可在真实开发流程中持续使用的内测产品”。

这一阶段不扩大高风险自治范围，而是提高 Harness 对不同仓库、不同模型和不同使用入口的适应能力，同时让质量、成本和失败原因可以被持续观察。

## 要做的事情

### 支持项目级指令

- 从仓库根目录到当前工作目录逐层加载 `AGENTS.md`。
- 更接近当前代码目录的项目规则具有更高项目优先级，但不能覆盖 Harness 安全规则。
- 每次模型调用可以解释加载了哪些指令、代码和历史信息。
- 上下文超限时优先裁剪可重新读取的输出和旧历史，保留当前目标与安全约束。

### 支持可复用 Skill

- 默认只发现 Skill 的名称、描述和路径。
- 只有任务匹配时才加载完整说明、引用和脚本。
- Skill 负责描述可复用工作流，不直接获得额外权限。
- 外部内容保持不可信状态，不能通过 Skill 或检索结果提升权限。

### 支持第二模型

- 在任务启动前检查模型是否支持所需的工具、上下文、流式输出和取消能力。
- 能力不足时在文件修改前明确失败。
- 不同模型复用相同的 Turn、工具、审批、ChangeSet 和验证链路。
- 模型专有参数保留在适配层，用户看到的任务状态和事件保持一致。

### 提供 CLI 与自动化入口

- 用户可以在当前目录发起一次代码任务。
- 用户可以恢复已有任务并查看状态、Diff 和验证结果。
- 机器消费模式提供稳定结构化输出和明确退出状态。
- CLI 与 Web 使用同一套任务服务，不形成独立的执行逻辑。
- 非交互环境遇到需要审批的动作时安全停止，不自动批准。

### 建立质量与成本反馈

- 按 Turn 关联模型调用、工具调用、命令、验证和最终结果。
- 展示任务完成情况、Diff 接受情况、恢复结果、执行耗时和成本。
- 为每个 Turn 记录模型、Prompt、工具、策略、工作流和数据集版本。
- 对模型、Prompt 或工具变更运行同一批回归任务，防止能力退化。
- 日志和 Trace 不保存密钥、隐藏推理或未经处理的敏感输出。

### 支持产品内测反馈

- 用户可以对结果标记接受、需要修改或无效。
- 失败任务能够定位在理解、工具、权限、执行、验证或交付阶段。
- 高频修正模式可以沉淀为项目指令、Skill 或评估案例。
- 产品版本是否继续扩展，以真实任务完成和安全数据为依据。

## 用户使用流程

```text
进入仓库或 CLI
  -> Harness 加载项目规则和匹配 Skill
  -> 校验所选模型能力
  -> 运行统一的安全交付流程
  -> 查看 Diff、验证、成本和版本信息
  -> 接受结果或继续修正
  -> 反馈进入回归评估与产品改进
```

## 交付形态

- 分层 `AGENTS.md` 与可解释 Context Snapshot。
- Repo Skill 发现和按需加载。
- 至少两个可比较的 Model Provider。
- `exec`、`resume`、`inspect` 等 CLI 能力。
- 结构化 Trace、指标和成本视图。
- 用户结果反馈与版本化回归评估。
- 可供真实仓库持续使用的内测版本。

## 完成标准

- 项目指令优先级明确且来源可追溯。
- 未匹配的 Skill 不进入完整上下文。
- 模型能力不兼容时在任何写入前失败。
- Web 与 CLI 对同一 Turn 展示一致的状态、事件、ChangeSet 和验证结果。
- 可以从 Turn 定位完整公开执行链和失败阶段。
- 敏感信息与隐藏推理不进入日志和 Trace。
- 每次模型、Prompt、工具或策略变化都有可复现的回归结果。
- 用户反馈可以转化为明确的产品改进输入。

## 本阶段不做

- 自动 commit、push、部署和永久审批。
- 多 Agent 并行编排。
- 云端执行环境和远程 Worker。
- IDE 插件和代码托管平台深度集成。
- 企业级 RBAC、集中策略和审计导出。
- 没有真实需求证据的插件市场或通用工作流 DSL。

## 后续演进方向

只有当内测数据出现明确需求时，才分别评估多 Agent、云执行、IDE 集成、Git 托管平台操作和企业治理。每项能力应作为独立产品闭环设计，不因为底层接口已经存在就默认进入下一版本。
