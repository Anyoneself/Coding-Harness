# 第二阶段：安全交付闭环

## 迭代定位

将产品从“能够持续运行的只读代码任务”迭代为“能够安全修改、验证并交付代码变化的 Coding Harness”。

这一阶段形成首个完整产品闭环：模型提出动作，Harness 负责校验、授权、执行和记录；用户可以查看 Agent 做了什么、为何需要确认、修改了哪些文件，以及验证是否通过。

## 要做的事情

### 建立统一工具执行链

- 所有文件、Git 和命令动作先经过参数校验。
- Harness 根据动作类型、影响范围和当前权限决定允许、询问或拒绝。
- Agent 不能直接调用底层执行器，也不能自行生成授权结果。
- 每次工具调用都有独立状态、结果和错误原因。

### 提供可理解的审批

- 审批界面展示具体动作、目标、规范化参数和风险原因。
- 用户可以仅批准一次，或批准当前 Turn 内同类动作。
- 动作参数、工作区或权限发生变化后，已有批准自动失效。
- 删除、提权、工作区外写入等高风险能力默认拒绝。

### 防止重复执行和误覆盖

- 相同工具调用重复到达时不会产生第二次副作用。
- 文件修改绑定读取时的内容基线。
- 用户在编辑器中同时修改文件时，Harness 停止覆盖并提示冲突。
- 写操作结果不确定时先核验实际状态，不盲目重试。

### 生成可审查的 ChangeSet

- 记录本 Turn 实际触碰的文件。
- 区分任务开始前已有改动和 Agent 新产生的改动。
- 展示新增、修改、删除和重命名文件。
- Git 项目展示完整 Diff；非 Git 目录提供等价的文件变化摘要。
- 大型 Diff 和命令输出支持按需加载。

### 提供验证证据

- Agent 可以运行与修改相关的测试、静态检查或构建命令。
- 每项验证展示命令、结果、耗时状态和必要的输出摘要。
- 非零退出结果不能显示为通过。
- 未运行验证时必须明确说明，而不是默认任务已验证。

### 形成 Coding Harness 工作台

- 左侧管理 Workspace 和 Thread。
- 中间展示对话、计划、工具执行和审批过程。
- 右侧集中展示文件变化、Diff 和验证结果。
- 页面刷新、网络重连和服务恢复后，仍以服务端任务状态为准。
- 用户可以基于本轮 ChangeSet 在同一 Thread 继续要求修正。

## 用户使用流程

```text
输入代码任务
  -> Agent 探索仓库
  -> Harness 校验工具动作
  -> 必要时请求用户审批
  -> 修改文件并检测冲突
  -> 运行测试或检查
  -> 交付 ChangeSet、Diff 和验证结果
  -> 用户审查并继续修正
```

## 交付形态

- 读、写、搜索、Git 和受控命令工具。
- 工作区权限模式和逐动作审批。
- 文件基线与并发冲突保护。
- ChangeSet、完整 Diff 和文件变化列表。
- Verification Summary。
- 支持审批、中断、恢复和审查的三栏工作台。
- 直接运行真实 Coding Turn 的评估体系。

## 完成标准

- 所有写入都能归因到对应 Turn 和 ChangeSet。
- 未授权动作无法执行，修改参数不能复用旧审批。
- 重复调用不会造成重复写入。
- 用户同时修改文件时不会被 Agent 静默覆盖。
- 页面重连后审批、工具状态和 Diff 保持一致。
- 失败测试和未运行验证均被准确展示。
- 安全评估中不存在工作区越界、审批绕过和范围外修改。

## 本阶段不做

- 永久批准和默认完全访问。
- 自动 commit、push、创建 PR 或部署。
- 多模型自动路由和运行中静默换模型。
- 完整 Skill、MCP 和多 Agent 体系。
- 云端 Worker、后台定时任务和企业权限管理。

## 下一迭代形态

在安全交付闭环稳定后，产品进入“可配置内测产品”：不同仓库可以沉淀项目规则和复用流程，用户可以从 Web、CLI 或自动化环境使用同一套 Harness，并能比较不同模型和版本的真实效果。
