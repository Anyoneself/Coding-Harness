# 调研报告

将调研结果沉淀为项目内可维护的中文文档，不要只在对话中返回临时结论。

## 输出位置

从当前工作区解析项目根目录；存在 Git 仓库时优先使用 Git 根目录。报告保存到：

```text
<project-root>/docs/<topic-slug>/research.md
```

按以下规则选择 `<topic-slug>`：

- 用户明确指定主题目录或输出路径时，遵循用户指定。
- 否则使用简短、稳定、小写英文 kebab-case 领域名称。
- 使用被调研的长期主题，不使用一次性问题或临时标题。
- 已存在语义相同的主题目录时复用，不创建同义目录。

示例：`evaluation`、`permissions`、`context-management`、`model-routing`。

如果 `research.md` 已存在，必须先阅读并整体更新：保留仍然有效的结论，修正过时内容，不在文件末尾追加一份互相割裂的新报告。

## 调研对象选择

- 优先选择与主题直接相关的行业知名实现和一手资料。适用时重点检查 OpenAI、Anthropic、Google、Microsoft/GitHub、Meta、Amazon 等公司的公开实现。
- 同时检查有行业影响力的开源项目、标准组织、正式论文和公认基准，例如 LangChain、Langfuse、OpenTelemetry、SWE-bench；仅在与主题相关时纳入。
- 通常至少覆盖 3 个具有代表性的实现；主题客观上不足 3 个可靠实现时，明确说明来源覆盖限制，不使用低质量案例凑数。
- 不因厂商知名而默认其方案更优。使用一致维度比较能力、架构、约束、成熟度和适用边界。
- 市场信息、产品能力、版本、价格和时间敏感内容必须重新检索，不能只依赖模型记忆。

## 来源优先级

按以下顺序选择证据：

1. 官方产品文档、API 文档、代码仓库和工程博客；
2. 标准规范、原始论文、官方基准仓库和公开技术报告；
3. 可靠的独立研究、会议资料或权威行业分析；
4. 二手文章只用于补充背景，不能单独支撑关键结论。

关键结论尽量由两个相互独立的一手来源交叉验证。只能找到单一来源时，标注“单一来源，待交叉验证”。无法找到可靠来源的内容只能写入“待确认”或“假设”，不得作为确定结论。

## 强制引用规则

- 每一条外部事实、产品能力描述、市场判断、对比结论和量化数据，都必须在同一段或同一表格行中附上对应参考网址或文献。
- Markdown 表格应增加“依据”列；如果多个相邻行共用来源，可在表格后逐行列出明确映射，但不能只给一组无法对应的链接。
- 综合结论必须引用支撑它的实现或文献。重要综合结论通常至少需要两个独立来源。
- 项目自身事实应引用仓库文件、代码位置、测试结果或提交；不要为本地事实伪造外部网址。
- 建议和优先级必须明确标注为“建议”，并引用其事实依据；纯粹的产品取舍可标注“项目判断”。
- 文末必须保留按类别整理的完整资料来源和访问日期，但文末来源列表不能替代正文就近引用。
- 链接文字应描述来源内容，避免使用“这里”“来源1”等无语义名称。
- 引用论文时至少写明标题、作者或机构、年份及 DOI、arXiv 或正式出版链接。

完成初稿后执行一次“结论到来源”检查：逐段检查每个事实和结论，确认读者不依赖文末猜测就能找到直接证据。

## 项目上下文

- 调研与当前项目有关时，先检查相关代码、架构文档、测试和配置，再判断项目差距。
- 明确区分外部事实、项目现状、综合分析、建议、假设和待确认问题。
- 不虚构产品能力、基准结果、价格、日期、项目状态或测试结果。
- 对实现进行比较时使用相同维度，并说明来源局限、版本差异和不可直接比较之处。

## 报告结构

用户指定格式时遵循用户格式。否则按主题实际需要选用以下部分，不为凑结构添加空章节：

1. 元信息：标题、状态、日期、范围和项目关联；
2. 执行摘要：结论及其直接依据；
3. 调研范围、方法和来源覆盖；
4. 市场或技术模式；
5. 代表性实现对比，包含逐项依据；
6. 对当前项目的影响和差距，包含本地代码依据；
7. 分级建议、验收标准和建议依据；
8. 风险、局限和待确认问题；
9. 分类资料来源与访问日期。

使用表格呈现真正需要横向比较的内容。报告应能作为后续设计和决策输入，不要写成搜索过程流水账。

## 完成检查

结束前必须确认：

- 报告存在于要求的路径；
- 知名代表性实现覆盖充分，并解释未覆盖项；
- 每项外部事实和结论都有就近参考网址或文献；
- 本地项目结论有文件、代码、测试或提交依据；
- 建议与市场事实明确分开；
- 链接可识别，资料来源包含访问日期；
- 最终回复提供报告的绝对可点击路径，并摘要最高影响结论。
