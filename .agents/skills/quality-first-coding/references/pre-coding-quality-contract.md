# 编码前质量契约

在修改生产代码前，于 `docs/quality/<change-slug>.md` 创建或更新本契约。模板用于保证关键决策完整，可以删除不适用部分，但必须写明关键检查为何不适用。

## 元信息

- 变更名称、负责人、日期、状态；
- 需求来源和关联任务；
- 影响模块、外部契约及明确不做的范围；
- 风险等级及判断依据。

## 需求与验收

使用可观察、可判定的描述，避免“正常工作”“性能良好”等模糊措辞。

| 需求 ID | 行为或约束 | 验收条件 ID | 可观察结果 | 测试/QA ID |
| --- | --- | --- | --- | --- |
| REQ-1 |  | AC-1 |  | UT-1 / GH-1 |

记录仍待确认的问题。会改变接口、数据语义、安全边界或实现方向的问题必须在编码前解决。

## 测试策略

### 单元测试

列出被测规则、输入类别、边界值、依赖替身、预期输出或异常。优先覆盖 Service 和 Domain 的分支决策，不直接绑定私有方法。

### 集成与契约测试

列出 Controller、Repository、数据库迁移、消息、缓存、第三方适配器、API/SSE/CLI 契约等跨边界行为。外部依赖默认使用可替换实现，不访问真实服务。

### Gherkin 验收场景

每个核心验收条件至少有一个场景，关键失败路径也应有场景：

```gherkin
Feature: <业务能力>

  Background:
    Given <稳定前置条件>

  Scenario: <用户可理解的结果>
    Given <初始状态>
    When <执行的业务动作>
    Then <可观察结果>
    And <需要保持的不变量>
```

避免在 Gherkin 中描述函数名、SQL 或内部类。注明场景由 BDD 运行器直接执行，还是映射到哪个集成/端到端测试。

### 测试数据与隔离

定义固定数据、工厂、清理策略、时钟和随机数控制、并发方式、敏感信息处理。测试不得依赖开发者本机状态、执行顺序、公网或真实 Token。

### 预实现失败证据

记录新增测试命令、失败测试、关键失败原因和日期。失败必须证明目标行为尚未存在，而不是语法、导入、环境或测试数据错误。

## QA 流程

1. 准备与生产等价的关键配置、权限矩阵和可重复测试数据。
2. 执行 smoke、核心 Gherkin 场景、负向/边界场景和受影响模块回归。
3. 验证日志、指标、Trace、告警和用户错误信息，不泄漏密钥或内部细节。
4. 保存命令输出、响应、截图或日志片段等可核验证据，并关联测试 ID。
5. 缺陷记录严重级别、复现步骤、责任范围、修复版本和回归结果。
6. 满足退出标准后完成发布前检查；不满足时阻断交付或由明确责任人接受风险。

## 变异测试计划

列出要扰动的关键规则，例如反转条件、删除权限检查、改变边界、跳过状态写入、移除异常处理或改变返回值。为每个变异注明应杀死它的测试 ID。

优先使用仓库已有变异工具。没有工具时，临时修改目标表达式执行对应测试后立即恢复，并保存结果；不要把人工变异提交到生产代码。

## 自动化检查矩阵

引用 `automated-quality-gates.md`，逐项填写：检查 ID、适用性、命令、预期阈值、执行阶段、阻断级别。未知命令先从项目配置和 CI 中发现，不臆造成功结果。

## 发布与残余风险

说明兼容性、迁移、功能开关、灰度、回滚、监控和告警。列出已接受风险、责任人和复查条件；没有则写“无”。

## 完成证据

实现后更新实际测试结果、覆盖率、变异分数、QA 结论、失败或跳过项。保持计划值和实际值可区分，不能覆盖原始门槛来迁就结果。
