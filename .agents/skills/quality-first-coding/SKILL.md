# 测试优先编码规范

以仓库现有架构和规范为准，在最小改动范围内完成可维护、可验证的生产代码。默认顺序是：契约与接口、Gherkin、测试、具体实现。

## 代码变更

- 需要在枚举、联合类型、消息类型、事件类型、协议类型或其他有顺序语义的数据结构中增添新类型时，只能在对应数据结构的最末端追加，禁止插入到已有类型中间。
- 采用增量更新，确保新增功能兼容已有代码逻辑、数据契约和调用方；禁止未经用户明确授权的破坏性变更。

## 开发规范

- 优先基于 Gherkin 场景进行测试驱动开发，先定义业务行为和验收条件，再编写可执行测试与实现。
- 测试用例必须覆盖完整的核心行为、关键失败路径、边界条件和 P99 场景，重点防止 panic、未处理异常、数据竞态、数据异常、状态不一致和资源泄漏。
- 每次变更保持范围可控并逐步验证，不得以实现新功能为由破坏已有兼容行为。

## 架构

- 代码设计和目录结构必须复用项目现有架构、分层和扩展方式。
- 如果实现确实需要新增现有架构之外或与当前需求无关的文件夹，必须先获得用户明确审批授权。

## 开发流程

### 1. 理解改动

- 阅读仓库约束、相关实现、调用链、数据契约和现有测试。
- 明确期望行为、失败语义、兼容性和受影响边界。
- 优先复用现有分层、命名、测试框架和工具，不为单次需求创建无实际价值的抽象或依赖。

### 2. 先定义契约与接口

- 在具体实现前明确输入、输出、错误、状态和副作用；HTTP、SSE、CLI、工具参数等边界使用明确 Schema。
- 对 Service、Repository、外部适配器、模型和工具边界优先定义最小接口，再由具体实现实现该接口。
- 上层依赖接口，通过装配或依赖注入选择具体实现；测试使用实现同一接口的 Fake 或 Stub。
- 接口按业务能力命名，不创建万能 CRUD、通用 `BaseService` 或只转发调用的包装层。
- 每个新增接口必须有当前需求中的真实调用者和至少一个具体实现，不添加占位接口或仅为未来扩展预留的抽象。
- 只有一个简单、稳定且无需替换的内部实现时，可直接使用具体类型；在提交说明中无需为未创建接口辩解。

### 3. 先写 Gherkin 和测试

- 所有新增或变更的业务行为必须先写 Gherkin 场景，至少覆盖主要成功路径和关键失败路径。
- 优先写入仓库已有 `.feature` 目录；没有约定时放入 `tests/features/<change-slug>.feature`。
- Gherkin 使用业务语言描述 `Given/When/Then`，不得出现函数名、SQL、内部类或实现步骤。
- 每个场景必须映射到可执行测试。仓库已有 BDD 运行器时实现对应 steps；没有时以场景标题或 ID 对应单元/集成测试，不仅保留文字场景。
- 纯内部重构未改变行为时可复用已有 Gherkin 场景，但必须运行其对应测试；若缺少场景则先补齐。

- 新功能先写最小的行为测试；缺陷修复先写能够复现问题的回归测试。
- 默认优先单元测试。跨数据库、HTTP、消息或外部适配器边界时，再增加必要的集成测试。
- 先运行新增测试，确认它因目标行为尚未实现而失败，而不是因语法、导入或环境问题失败。
- 测试面向可观察行为，覆盖主要成功路径、相关边界和明确失败路径，不重复绑定内部实现细节。
- 不为解析 Gherkin 强行引入大型依赖；没有 BDD 运行器时保持场景与普通可执行测试的一一映射。

无法合理编写预实现测试时，先简要说明原因和替代验证，再修改生产代码。纯重命名、注释或机械格式调整可直接执行已有检查。

### 4. 编写具体实现

- 只实现让测试通过所需的最小完整行为，避免顺手重构无关模块。
- 保持 Controller、Service、Domain、Repository、Infrastructure 和 CLI 的职责与依赖方向清晰。
- 具体实现遵守已定义接口，不向上层泄漏 SQL、SDK 响应、游标或框架对象。
- 业务规则只保留一份；输入适配层不得复制 Service 或 Domain 逻辑。
- 使用清晰命名、完整类型和仓库要求的文档字符串；避免模糊字典、魔法值和可变默认参数。
- 使用守卫语句和小函数降低嵌套。只有在确实降低复杂度或消除重复时才增加抽象。
- 外部输入必须校验；文件、命令、数据库和权限操作遵守安全边界；外部调用设置超时并避免敏感日志。
- 尊重工作区已有改动，不覆盖或回退不属于当前任务的内容。

### 5. 运行并整理

- 每个小增量后运行相关测试，测试通过后再做必要的局部整理。
- 整理不得改变已验证行为；若行为发生变化，先补充或更新测试。
- 接口、Schema、CLI 输出或配置发生变化时，同步更新对应调用方、示例和文档。

### 6. 完成验证

- 运行受影响测试、仓库规定的全量测试和静态检查。
- 覆盖率用于发现遗漏，不为追求数字添加无意义测试；变更代码不应降低已有覆盖质量。
- 对权限、状态转换、幂等、资金、数据一致性等关键规则，或仓库已有变异工具时，执行定向 Mutation Testing 并处理非等价存活变异。普通低风险改动不强制引入变异工具。
- 按风险补充契约、安全、迁移、并发、性能或端到端验证，不机械执行与改动无关的检查。
- 最终准确说明改动、测试结果、未执行项和残余风险，不声称未运行的检查已通过。

## Agent/Harness 代码

模型、工具调用或工作流编排必须先定义可替换接口，再提供真实实现和测试替身。重点验证结构化输出、畸形工具参数、工具权限与确认、超时重试、流式事件和会话恢复；默认测试不访问公网或消耗真实 Token。
