# 质量优先编码

把质量设计作为编码输入，而不是开发结束后的补充。先证明需求可验证，再修改生产代码。

## 不可跨越的门禁

在修改生产代码前，必须完成以下事项：

1. 阅读仓库约束、相关入口、调用链、契约、测试和构建配置。
2. 创建或更新 `docs/quality/<change-slug>.md` 质量契约；同一主题复用现有文档。
3. 将需求映射到单元测试、Gherkin 场景、QA 检查和量化退出标准。
4. 优先编写并运行最小失败测试，确认它因目标行为缺失而失败；缺陷修复必须先有回归测试。

完成这些事项前，不得编辑生产代码。若任务客观上无法编写可执行的预实现测试，应在质量契约中记录原因、替代验证和残余风险，然后才可继续。用户明确要求跳过某项门禁时，遵循用户要求并说明风险，不得暗中省略。

## 工作流程

### 1. 建立需求与风险模型

- 提炼行为需求、非功能需求、失败语义、兼容性和明确不做的范围。
- 标出受影响的 Controller、Service、Domain、Repository、DB、CLI、工具、Agent 和前端契约。
- 检查仓库已有测试框架、覆盖率工具、静态检查、CI 命令和当前基线，不凭空假设工具可用。
- 按 [自动化质量门禁](references/automated-quality-gates.md) 选择风险等级和检查集合。

### 2. 编写编码前质量契约

阅读 [质量契约模板](references/pre-coding-quality-contract.md)，按需求保留有意义的部分。质量契约必须在任何生产代码改动之前落盘，并至少包含：

- 可追踪的需求与验收条件；
- 正常、边界、错误和安全路径；
- 单元、集成、契约、端到端及 Gherkin 场景的分工；
- QA 环境、数据、执行步骤、证据和缺陷闭环；
- 覆盖率、变异分数、性能、可靠性等适用指标及阈值；
- 自动化检查命令、失败阻断规则和无法执行项；
- 发布、回滚、可观测性和残余风险。

使用稳定 ID 建立追踪关系，例如 `REQ-1`、`AC-1`、`UT-1`、`GH-1`、`QG-1`。每个验收条件必须至少对应一个测试或 QA 检查。

### 3. 先实现测试侧证据

- 在最合适的测试层验证可观察行为，不为追求数量重复测试同一实现细节。
- 仓库已有 BDD 运行器时，先添加 `.feature` 和步骤实现；没有时，将 Gherkin 作为可审查的验收规范，并映射到可执行的集成或端到端测试。
- 不仅验证成功路径，还要覆盖输入校验、依赖失败、权限、幂等、超时、重试、并发和敏感信息处理等适用风险。
- 运行新增测试并记录预实现失败证据。若测试意外通过，检查需求是否已实现或测试是否缺乏辨别力。
- 不为一个简单场景擅自引入大型测试依赖；确有必要时先说明用途、维护成本和替代方案。

### 4. 最小增量实现

只实现让当前失败测试通过所需的生产改动，并遵循仓库分层、类型、文档字符串和安全规范。每个小增量后运行相关测试，保持失败定位清晰。需求或实现边界变化时，先更新质量契约和测试，再继续编码。

### 5. 执行质量门禁

按 [自动化质量门禁](references/automated-quality-gates.md) 执行已承诺检查，包括定向测试、全量回归、覆盖率、变异测试和适用的静态、安全、契约、性能或可靠性检查。

- 变异测试必须针对本次修改的业务规则和关键分支执行；没有现成工具时进行人工定向变异抽样，并记录变异、预期杀死它的测试和结果。
- 覆盖率只作为缺口信号，不可用无断言测试、排除标记或无意义分支提高数字。
- 修复所有由本次变更引入的失败。既有失败必须与本次变更区分并提供证据，不能笼统归因于环境。

### 6. 完成交付闭环

最终说明：实现行为、质量契约位置、新增测试、各门禁结果、覆盖率与变异分数、未执行项及原因、残余风险。不得声称未实际运行的检查已通过。

## Harness/Agent 额外关注

涉及模型、工具调用或工作流编排时，把以下内容纳入质量契约：确定性模型替身、结构化输出校验、畸形工具参数、工具权限与确认、提示注入、超时与重试、流式事件顺序、会话持久化、敏感信息脱敏，以及默认测试不访问公网或消耗真实 Token。
