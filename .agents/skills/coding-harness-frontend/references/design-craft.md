# 前端设计与审美判断

本文件用于新页面、视觉重构、组件样式、空状态和动效任务。目标不是让界面“更像 AI
生成的设计稿”，而是让它更像长期使用后仍然顺手、清楚且有自身气质的工程产品。

## 1. 先确定视觉命题

编码前写下五项简短判断，不需要生成面向用户的长篇设计说明：

1. **用户：** 谁会长时间使用这个页面，他们此刻在判断或完成什么？
2. **焦点：** 第一眼应该落在哪里？一个页面只能有一个主要视觉焦点。
3. **密度：** 当前场景更需要沉浸、扫描、比较还是编辑？
4. **性格：** 用三个具体形容词描述气质，例如“冷静、精密、轻盈”，避免“现代、高级、
   简洁”这类无法指导取舍的词。
5. **克制项：** 明确本次不使用什么，例如“不使用同构卡片、不使用装饰标签、不使用
   大面积渐变”。

设计来自任务内容，而不是来自组件模板。Coding-Harness 的视觉线索可以来自代码结构、
终端节奏、执行序列、文件层级、Diff 和验证证据，但不要把这些线索全部同时画出来。

## 2. 形成正向辨识度

新页面或明显视觉重构不要直接落入第一个方案。先提出两个结构或气质明显不同、但都符合真实
能力的方向，例如：

- **执行画布方向：** 把持续输出、状态变化与证据阅读作为中心，导航与输入退居辅助。
- **工程入口方向：** 把项目上下文和任务输入作为中心，执行信息在任务开始后逐步显现。

方向必须来自当前任务，不固定使用以上示例。比较时回答：

- 哪个方向更支持当前用户的主要动作？
- 哪个方向能利用真实的 Workspace、Thread、Turn 或 Event，而不伪造未来能力？
- 哪个方向有一个可以被记住的标志性表达？
- 替换 Logo 和产品名后，它是否仍然像任何通用 AI 聊天页面？

选择一个方向后，把辨识度集中到一个表达上，例如执行流的节奏、输入器与工程上下文的关系、
证据阅读方式或侧栏的信息组织。不要把“辨识度”理解为增加更多装饰。

## 3. 建立紧凑的视觉系统

### 3.1 色彩

- 使用 4 至 6 个有明确职责的基础颜色：画布、表面、主要文字、次要文字、边界、强调色。
- 状态色表达稳定语义：成功、等待、警告、失败不能仅靠明暗差异区分。
- 强调色只用于当前选择、主要动作和关键状态。大面积使用会让每个区域都失去重点。
- 渐变、纹理和流体背景只有在承担品牌识别或空间组织时才使用；正文与高频操作区域必须
  保持足够平静。
- 检查整屏色彩分布，避免只在一种色相上堆叠十几个相近色值而显得单调。

### 3.2 字体

- 中文正文优先稳定、清晰的无衬线字体栈；代码、路径和 ID 才使用等宽字体。
- 建立有限字号层级，通常包括页面标题、区域标题、正文、辅助文字和数据文字。
- 不使用负字距，不按视口宽度连续缩放字号。
- 标题是信息，不是装饰。避免每个区域都添加英文全大写眉题、点分隔元信息或“AI
  ENGINEERING WORKSPACE”式标签。
- 正文行长保持适于阅读，长标题使用平衡换行；数字比较场景使用等宽数字。

### 3.3 空间与边界

- 先用对齐、间距和背景层次分组，再考虑边框和卡片。
- 页面区段默认不做悬浮卡片；卡片只用于独立重复项、模态框和确实需要框定的工具。
- 不在卡片中继续嵌套卡片。层级过深时改用分隔线、留白、缩进或切换视图。
- 圆角按对象尺度分级，小控件、小面板和模态框不应共享同一个夸张圆角。
- 阴影表示真实层级，例如浮层覆盖或输入器悬浮；静态列表不需要每项都有阴影。

## 4. 避免模板化 AI 痕迹

出现以下组合时，先停下来重新判断，而不是继续润色：

- 蓝紫渐变背景、发光球体、玻璃卡片和白色大标题同时出现。
- 页面内容被切成三张或四张尺寸相同、圆角相同、文案结构相同的卡片。
- 每个标题上方都有全大写英文标签，每个按钮后都有箭头。
- 用大量“智能、赋能、无缝、下一代、释放潜力”描述产品，却没有真实操作和状态。
- 所有图标都放进有底色的小圆角方块，所有状态都做成胶囊标签。
- 聊天机器人头像、星光图标和思考气泡成为默认品牌语言。
- 为了显得丰富而同时加入网格、光晕、流体、粒子、渐变和动态边框。
- 空状态展示功能介绍卡片，而不是让用户直接开始核心任务。

修正顺序：

1. 删除不帮助操作的文案。
2. 移除一半容器，恢复页面结构和留白。
3. 只保留一个主视觉手段。
4. 拉开字体、明暗和间距层级，而不是继续加装饰。
5. 用真实项目名、状态和任务内容验证界面，而不是使用营销占位文本。

## 5. Coding-Harness 的界面语法

### 5.1 工作台

- 宽屏把 Thread 导航、执行画布和检查器看作三个职责区域，不把它们都做成同权面板。
- 执行画布拥有最大视觉权重；导航安静稳定；检查器按需覆盖，避免持续挤压正文。
- 空任务的核心是项目上下文与输入器。中央最多保留一句能推动行动的提问，不再解释 Harness
  如何工作。
- 有对话后，输入器收敛到稳定阅读宽度；消息内容以文章流展示，不把每条 Assistant 回复
  包成聊天气泡。

### 5.2 执行状态

- 状态反馈应回答三个问题：现在发生什么、是否需要用户行动、接下来会怎样。
- 长任务用连续时间线或阶段变化表达，不用散落的旋转图标制造忙碌感。
- 当前状态可以有一次克制动效；历史状态保持静态。
- 错误靠位置、图标、标题和恢复动作共同表达，不能只把整块区域染红。

### 5.3 输入器

- 输入器是工作台的主要工具，不是普通聊天文本框。项目、权限或模型上下文只展示当前操作
  真正需要确认的信息。
- 空状态输入器可以更宽、更有存在感；进入会话后应缩小并让位于执行内容。
- 附件、工具、模型和发送操作按使用频率组织。不要为了对称把每个入口都放进独立胶囊。
- 发送与中断是同一主操作位置的显式状态切换，尺寸不得变化导致布局跳动。

## 6. 动效

- 动效解释关系、状态或空间变化。没有信息变化时，不让元素持续漂浮、呼吸或闪烁。
- 优先设计一个编排完整的进入时刻，或一个响应用户操作的局部反馈。
- 动画持续时间、位移和缓动保持一致；避免每个卡片各自淡入上移。
- 使用 `transform` 与 `opacity`，避免触发布局的属性。
- 所有非必要动效在 `prefers-reduced-motion` 下停止或缩短。
- 装饰循环超过 5 秒且与内容并存时，提供暂停方式；更推荐静态质感。

## 7. 文案

- 一个文本元素只完成一个任务：命名、说明、状态、警告或动作。
- 使用主动语态和具体动词，如“配置 API Key”“中断任务”“重新连接”。
- 同一动作在按钮、状态和反馈中保持相同名称。
- 空状态给出下一步；错误说明原因范围和可执行的恢复方式；成功反馈不重复页面上已经明显
  可见的结果。
- 不用文案解释视觉特效、键盘布局或产品“简洁优雅”等设计意图。

## 8. 截图复盘

视觉任务完成前，至少检查一个桌面截图和一个移动截图，并回答：

- 眯眼看时，第一视觉焦点是否正确？
- 去掉颜色后，层级是否仍由尺寸、位置和空间成立？
- 是否存在没有信息价值的卡片、标签、说明或图标底板？
- 最长项目名、长消息、错误文本和空数据是否破坏布局？
- 输入器、导航和检查器是否在不同状态间发生尺寸跳动？
- 页面是否具有 Coding-Harness 的工程语境，而不是可以替换 Logo 后用于任何 AI 产品？
- 最终方案是否继承了所选方向的标志性表达，而不是在实现中退回通用组件模板？

发现问题后先删减，再调整层级，最后才增加视觉元素。
