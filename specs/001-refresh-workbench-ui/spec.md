## User Scenarios & Testing *(mandatory)*

### User Story 1 - 从品牌空状态发起任务 (Priority: P1)

作为本机开发者，我希望打开一个尚无消息的任务时，首先看到与参考图一致的浅蓝流光工作台、清晰的产品身份、当前项目上下文和居中的任务输入器，从而不需要寻找入口即可开始描述开发目标。

**Why this priority**: 新任务发起是工作台最核心、最高频的入口，也是本次视觉迭代能否产生用户价值的主要判断标准。

**Independent Test**: 在模型已就绪且当前任务无公开消息时打开工作台，验证首屏可识别产品、项目、模型和唯一主输入入口，并可直接提交任务。

**Acceptance Scenarios**:

1. **Given** 模型已就绪且当前任务没有公开消息，**When** 用户打开桌面工作台，**Then** 页面应展示浅蓝流光背景、Coding-Harness 品牌标识、任务导向主标题和位于首屏视觉中心的任务输入器。
2. **Given** 用户位于空任务首屏，**When** 用户查看输入器上下文，**Then** 应看到来自真实配置的当前项目和模型信息，且页面不得显示静态伪造的项目、分支或模型值。
3. **Given** 用户已输入非空任务目标，**When** 用户发送任务，**Then** 系统应沿用现有任务创建与 Turn 执行流程，并在同一工作台框架内进入执行态。
4. **Given** 模型尚未完成配置，**When** 用户尝试发送任务，**Then** 系统应引导用户完成现有安全配置流程，且不得把凭据显示或持久化在工作台导航、任务历史或输入器中。

---

### User Story 2 - 在统一框架中浏览与管理任务 (Priority: P2)

作为持续处理多个代码任务的开发者，我希望通过参考图式的左侧导航快速创建任务、识别当前任务、切换最近任务并确认当前项目，而中央工作区保持稳定，不因导航操作产生混乱。

**Why this priority**: 持续任务历史是 Coding-Harness 区别于一次性聊天框的重要产品能力，稳定导航直接影响重复使用效率。

**Independent Test**: 准备多个本地任务记录，在非运行状态下完成新建、选择和移除操作，并验证活动项、任务状态和当前项目始终清晰。

**Acceptance Scenarios**:

1. **Given** 浏览器中存在多个结构合法的最近任务，**When** 用户打开左侧导航，**Then** 任务应按最近更新时间分组展示，当前任务应具有明确且不只依赖颜色的选中状态。
2. **Given** 当前没有任务正在运行，**When** 用户选择另一项最近任务，**Then** 中央工作区应切换到对应公开消息历史，并关闭移动端任务导航。
3. **Given** 当前没有任务正在运行，**When** 用户新建或移除任务，**Then** 导航和中央工作区应同步更新，且移除最后一个任务后仍保留一个可输入的新任务。
4. **Given** 当前 Turn 正在运行，**When** 用户尝试切换、移除或新建其他任务，**Then** 会破坏当前执行上下文的操作应保持禁用，当前运行任务仍可被观察和中断。
5. **Given** 当前只存在一个真实 Workspace，**When** 用户查看“项目”区域，**Then** 页面只应展示该真实项目，不得根据参考图虚构多项目列表或切换能力。

---

### User Story 3 - 查看执行态与检查器 (Priority: P2)

作为正在等待 Agent 执行的开发者，我希望任务开始后仍保留浅蓝流光的产品视觉，同时让消息、运行状态、中断操作、执行事件和 Turn 信息易于阅读和按需查看。

**Why this priority**: 工作台不仅要有漂亮的空状态，还必须承载真实、持续且可恢复的执行过程。

**Independent Test**: 使用可控公开事件运行一个 Turn，验证消息流、状态更新、中断入口和按需检查器在同一框架内工作，且不会永久压缩主阅读区。

**Acceptance Scenarios**:

1. **Given** 当前任务已出现公开消息，**When** 工作台进入执行布局，**Then** 消息列表应替代空状态主标题成为主要内容，任务输入器移动到执行区域底部且保持同一提交行为。
2. **Given** Turn 正在流式执行，**When** 公开事件按序到达，**Then** 用户应看到可理解的运行状态和公开回答，背景装饰不得降低正文、状态或控制按钮的可读性。
3. **Given** 用户选择“执行事件”或“Turn”顶部导航，**When** 检查器打开，**Then** 应直接选择对应的现有检查器标签，并以覆盖式面板呈现，不永久改变主画布宽度。
4. **Given** 检查器已打开，**When** 用户关闭检查器或返回“工作台”，**Then** 主画布应恢复完整可用宽度，当前消息、输入内容和执行状态不得丢失。
5. **Given** Turn 正在运行，**When** 用户激活输入器主操作按钮，**Then** 该按钮应明确表示并执行中断操作，而不是继续提交第二个并发 Turn。

---

### User Story 4 - 在不同视口下完成核心流程 (Priority: P3)

作为使用笔记本或窄屏设备查看本机任务的开发者，我希望工作台在桌面和移动视口下都保持清晰、无横向溢出，并能独立访问任务导航与执行检查器。

**Why this priority**: 响应式布局不是桌面视觉还原的附属项；窄屏下仍需可靠完成任务输入、观察和控制。

**Independent Test**: 分别在 1680×941、1024×768 和 390×844 视口完成新任务输入、打开与关闭两侧导航、查看执行消息及中断操作。

**Acceptance Scenarios**:

1. **Given** 用户在宽桌面视口打开空任务，**When** 页面完成布局，**Then** 左侧任务导航、顶部主导航、主标题和宽输入器应形成与参考图一致的稳定层级，并在首屏保留足够操作空间。
2. **Given** 用户在 390×844 视口打开工作台，**When** 页面完成布局，**Then** 左侧任务导航和执行检查器应默认离开主画布，并通过两个具有明确可访问名称的独立控件打开。
3. **Given** 任一移动端抽屉已打开，**When** 用户关闭抽屉、点击遮罩或切换内容，**Then** 抽屉应退出且焦点仍可继续用于中央任务流程。
4. **Given** 用户在支持的任意视口输入长文本或查看长任务名称，**When** 内容接近容器边界，**Then** 文本应换行、截断或滚动，不得遮挡相邻控件或造成页面横向溢出。

### Edge Cases

- 浏览器保存的任务历史 JSON 损坏、含敏感字段、字段缺失或超过数量限制时，工作台应忽略无效记录并保持可用，不展示原始异常内容。
- 公开配置读取失败时，页面应给出可理解的连接错误；导航和背景仍可显示，但发送动作不得表现为成功。
- Workspace 根路径为空、过长或包含多字节字符时，项目名称应稳定显示并提供可访问的完整上下文，不撑破布局。
- 当前模型名称过长或暂时不可用时，输入器应保持尺寸稳定，并使用明确的读取中或未就绪状态。
- SSE 重复、倒序、未知或中断后迟到的公开事件不得造成消息重复、状态回退或布局跳动。
- 用户启用减少动态效果偏好时，流光背景应停止或显著减弱运动，同时保留视觉层级和内容可读性。
- 背景资源无法加载时，页面仍应提供完整操作能力、足够对比度和稳定布局。
- 键盘用户在导航、输入器、发送或中断按钮、抽屉和配置对话框之间移动时，应始终看到明确焦点且不会陷入不可退出区域。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须把空任务首页呈现为参考图式的浅蓝流光工作台，包含显著的 Coding-Harness 品牌、任务导向主标题和首屏主输入器。
- **FR-002**: 系统必须在桌面端提供固定左侧任务导航、顶部主导航和完整中央任务画布，并保持三者边界清晰、层级稳定。
- **FR-003**: 左侧任务导航必须提供新建任务、最近任务、活动任务状态和当前项目信息；所有内容必须来自现有任务历史或公开配置。
- **FR-004**: 顶部主导航必须只映射已经存在且可工作的工作台、执行事件和 Turn 视图；不得展示不可操作的“评估”“工具”、搜索、设置或账户入口。
- **FR-005**: 空状态主输入器必须显示真实的当前项目和模型上下文，并提供任务文本输入以及一个明确的发送主操作。
- **FR-006**: 当真实分支信息未由现有产品契约提供时，系统不得显示伪造分支名称或可交互分支选择器；未来增加分支能力需单独变更规格与契约。
- **FR-007**: 用户发送首条任务后，系统必须在同一工作台框架内从空状态过渡到执行态，不进行整页跳转，也不重置已建立的任务上下文。
- **FR-008**: 执行态必须展示当前任务的公开消息、运行状态和输入器；输入器应位于消息阅读区域底部并保持空状态下的核心输入语义。
- **FR-009**: 当 Turn 正在运行时，主操作必须转换为明确的中断操作，并阻止会创建同一 Thread 并发 Turn 或切走当前执行上下文的任务操作。
- **FR-010**: “执行事件”和“Turn”导航必须复用现有检查器能力，并在打开时选择相应标签；检查器关闭后不得永久占用中央画布宽度。
- **FR-011**: 系统必须在移动端将任务导航和执行检查器作为相互独立的按需抽屉，并为打开、关闭和遮罩操作提供可访问名称。
- **FR-012**: 页面必须在 320 像素及以上视口避免横向页面溢出；任务名称、项目名称、模型名称、消息和输入文本不得与其他控件重叠。
- **FR-013**: 所有图标按钮必须具有可感知的名称或提示；当前导航项、当前任务、禁用状态、运行状态和错误状态不得只通过颜色表达。
- **FR-014**: 文本与关键控件在背景和半透明表面上必须保持清晰可读，键盘焦点必须始终可见，交互目标应适合鼠标和触摸操作。
- **FR-015**: 系统必须尊重用户的减少动态效果偏好；关闭装饰动画后不得影响任务创建、事件观察或中断操作。
- **FR-016**: 背景视觉、半透明输入器或装饰资源加载失败时，工作台必须降级为可读、可操作的静态界面。
- **FR-017**: 本次迭代必须保持现有 Workspace、Thread、Turn、公开事件、API Key 配置、本地任务历史和中断行为的用户可观察语义。
- **FR-018**: 系统不得在界面、浏览器持久化数据或用户可见错误中暴露 API Key、隐藏推理、内部堆栈或不应公开的本机路径细节。
- **FR-019**: 所有视觉与交互验收必须覆盖空状态、执行态、检查器打开态、配置未就绪态和连接失败态，避免只对静态首页截图成立。

### Compatibility Boundaries

- 保留现有任务历史数据的读取兼容性；旧记录缺少纯展示字段时可安全补齐，结构不可信时应忽略。
- 保留现有任务发送、Enter 发送、Shift+Enter 换行、Turn 中断、SSE 归约和首次 API Key 配置流程。
- 保留 Web 工作台对当前单 Workspace、单活动 Turn 和公开事件协议的现有约束。
- 视觉重构不得要求后端先提供多项目、分支列表、评估中心、工具中心、搜索、账户或设置能力。

### Failure Behavior

- 配置、任务创建、Turn 创建、事件连接或中断请求失败时，用户必须看到面向操作的错误状态，界面不得停留在虚假的运行中或成功状态。
- 可恢复的视觉资源失败不得阻断业务操作；业务依赖失败则必须禁用不安全或不可能成功的提交动作。
- 执行期间被禁用的任务管理操作必须保持一致，不得出现按钮可点击但结果被静默忽略的歧义反馈。

### Out of Scope

- 新增评估中心、工具中心、全局搜索、设置中心、用户账户或通知系统。
- 新增多 Workspace 管理、项目扫描、项目切换、Git 分支发现或分支切换。
- 新增模型 Provider 或模型切换契约。
- 修改后端执行状态机、SSE 事件格式、权限策略、持久化模型或 CLI 行为。
- 在本次规格中实现参考图里没有真实产品能力支撑的装饰性假按钮。

### Key Entities *(include if feature involves data)*

- **Workspace**: 当前 Agent 可访问的真实项目边界；工作台使用其公开根目录推导项目显示名称，但不扩展为多项目管理。
- **Thread（任务）**: 围绕持续目标的任务历史；包含本地显示标识、服务端 Thread 标识、标题、状态、更新时间和公开消息。
- **Turn**: 一次用户输入触发的执行；工作台展示其公开状态、事件、结果和中断能力。
- **Workbench View**: 用户当前选择的工作台、执行事件或 Turn 视图；后两者映射到同一个按需检查器的不同标签。
- **Public Configuration**: 可向当前用户展示的模型就绪状态、模型名称和 Workspace 根目录；不包含 API Key 或隐藏推理。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在 1680×941 视口的可用性测试中，至少 90% 的首次使用者能在 10 秒内识别当前项目、模型和任务输入入口，并成功开始输入任务。
- **SC-002**: 在 390×844、1024×768 和 1680×941 三种验收视口中，核心任务流程均无页面级横向溢出、控件遮挡或不可访问的主操作。
- **SC-003**: 用户可在 2 次操作内从工作台打开执行事件或 Turn 详情，并在 1 次操作内关闭检查器返回完整主画布。
- **SC-004**: 空状态到执行态的转换不丢失任务文本、当前任务身份或公开执行状态；重复验收 20 次时成功率为 100%。
- **SC-005**: 对照参考图进行评审时，品牌、左侧导航、顶部导航、主标题、宽输入器和浅蓝流光背景六项核心视觉信号全部可在桌面首屏辨认；不要求逐像素复制参考图。
- **SC-006**: 使用键盘完成新建任务、输入、发送或中断、打开和关闭两侧面板的关键流程时，100% 的交互步骤具有可见焦点和可感知名称。
- **SC-007**: 配置未就绪、配置读取失败、事件连接失败和背景资源失败四类场景均保持可理解反馈，其中背景资源失败不阻断任何核心任务操作。
- **SC-008**: 回归验收确认现有任务历史恢复、SSE 顺序归约、API Key 不落浏览器持久化和运行中断四项行为无变化。

## Assumptions

- 参考图用于约束视觉语言、信息层级、布局比例和交互重心；验收采用设计语言对齐，不要求逐像素复制，细节可根据现有真实能力与响应式可用性调整。
- 本次迭代面向现有单 Workspace Web 工作台，当前项目来自公开配置，最近任务来自浏览器中经过校验的本地历史。
- 顶部导航继续使用“工作台”“执行事件”“Turn”，以真实能力替代参考图中的“评估”“工具”示意入口。
- 输入器中的第二个上下文标签继续表达现有 Workspace 执行边界；只有未来契约提供真实 Git 分支数据后，才可替换或增加分支信息。
- 桌面参考验收以用户提供的 1680×941 图像为主要视觉基准，同时必须适配常见笔记本和移动视口。
- 浅蓝流光可以是静态或轻量动态视觉；减少动态效果偏好、性能不足或资源失败时允许降级为静态背景。
- 本次变更复用现有公开配置、任务历史和执行接口，不要求后端新增业务能力。
