# Phase 0 Research: 参考图升级前端工作台

## 决策 1：采用“工程入口画布”

**决策**：空 Thread 以真实 Workspace 上下文、任务导向标题和宽输入器为第一视觉焦点；任务开始后在同一框架内转换为公开消息与执行状态阅读流。

**理由**：

- 最接近参考图的结构和交互重心。
- 直接服务当前用户的首要动作：确认项目和模型后发起代码任务。
- 可以完全使用现有 Workspace、Thread、Turn、Event 和公开配置，不需要虚构未来能力。
- 输入器与工程上下文的关系形成产品辨识度，避免退化为通用聊天首页。

**考虑过的替代方案**：

- **执行证据画布**：让 Event 时间线和 Turn 状态主导首屏。该方向更适合未来具备 Diff、Verification 和审批后的完整执行台；当前空 Thread 缺少足够真实证据，会形成无效区域并暗示未实现能力。
- **仅换配色**：保留当前布局，只增加浅蓝背景。改动不足以满足参考图的信息层级和首屏任务入口目标。

## 决策 2：设计语言对齐而非像素级复刻

**决策**：保留品牌、左侧导航、顶部导航、主标题、宽输入器和浅蓝流光背景六个核心信号；尺寸、间距和控件内容根据现有真实能力、长文本和响应式可用性调整。

**理由**：

- 已由 2026-09-05 澄清会话确认。
- 参考图含评估、工具、多项目和分支等当前不存在的能力，逐项复刻会产生假入口。
- 响应式布局、中文文本长度和可访问性要求需要允许细节调整。

**考虑过的替代方案**：

- **1680×941 高保真复刻**：会增加脆弱的固定尺寸和无业务支撑的装饰控件。
- **自由改版**：缺少可验证的视觉基准，无法证明满足用户提供参考图的意图。

## 决策 3：复用现有静态流光资产作为唯一主视觉

**决策**：继续使用 `frontend/public/workbench-flow.webp`，在空状态保持可辨认，在执行态降低对比度；不新增第二套背景、粒子、光球或循环漂移动画。

**理由**：

- 资产尺寸为 1672×941，与参考图桌面比例一致。
- 静态资源不占用持续动画预算，天然兼容 reduced-motion。
- 一个主视觉足以承担品牌识别，其余区域应保持安静、可扫描。

**考虑过的替代方案**：

- **CSS 多层渐变**：容易形成单一蓝色渐变模板感，并增加跨浏览器差异。
- **持续动态流体背景**：会干扰消息阅读、增加性能风险和 reduced-motion 处理成本。
- **重新生成图片**：现有资产已符合目标，本次没有新增素材需求。

## 决策 4：收敛现有 CSS 级联，不继续追加覆盖层

**决策**：整理 `frontend/src/styles.css` 中本功能涉及的 Token、布局、状态和响应式规则，合并“流光玻璃工作台视觉层”和“参考图版式对齐”等重复覆盖；保持未受影响的 Markdown、表单和检查器内容样式在原职责内。

**理由**：

- 当前文件存在多轮相同选择器覆盖，最终行为依赖源顺序，增加桌面、移动和矮屏之间的回归风险。
- 本功能同时改变空状态、执行态、侧栏、顶栏、输入器和抽屉，继续追加规则会使验收难以归因。
- 局部收敛可提升可维护性，又不扩大为无关全量重构。

**考虑过的替代方案**：

- **继续追加第三层覆盖**：短期改动小，但会加剧冲突并使响应式测试不稳定。
- **拆分完整设计系统**：当前只有一个页面和少量组件，没有足够调用场景支撑新抽象。

## 决策 5：保持组件与状态边界

**决策**：继续由 `App.tsx` 编排共享状态，`api/` 负责 HTTP/SSE，`domain/` 负责事件与本地历史归约，现有区域组件负责展示和局部交互；不引入全局状态库、Context Provider 或页面路由。

**理由**：

- 当前页面规模和状态所有权清晰，新增状态层不能降低真实复杂度。
- 功能主要是视觉层级、显式界面状态和错误表现，不需要改变领域模型。
- 保持单向依赖符合项目 Constitution 和现有测试方式。

**考虑过的替代方案**：

- **新建 Workbench Store**：只会包装现有 `useState`，缺少第二个消费页面。
- **拆分空状态和执行态页面路由**：会破坏同一 Thread 框架内自然过渡的需求。

## 决策 6：保持公开接口与存储 Contract 不变

**决策**：不修改后端 API、Schema、Service、Repository、DB 或 CLI；保留现有 localStorage 结构和最多 30 个本地 Thread 的限制。

**理由**：

- Spec 明确本次为 Web 工作台视觉与交互升级。
- 当前公开配置已提供真实项目根目录、模型和就绪状态。
- 当前 API 已支持任务创建、Turn 执行、事件流和中断，足以完成目标。

**考虑过的替代方案**：

- **增加分支或项目列表接口**：属于独立产品能力，超出范围。
- **增加服务端 Thread 历史接口**：会改变持久化和跨端语义，不应由视觉需求带入。

## 决策 7：非终态 SSE 断流在前端显式失败

**决策**：事件流正常结束后，若最后状态不是 `completed`、`failed`、`interrupted` 或 `cancelled`，前端将其视为连接失败并保留已收到的公开内容，不把部分回答持久化为成功结果。

**理由**：

- 后端 Contract 约定终态后才关闭 SSE；非终态 EOF 表示连接或服务异常。
- 当前 `streamTurnEvents` 返回后会直接使用部分回答，可能让界面显示虚假完成。
- 该处理可在现有 API 与执行状态模型内完成，不需要新增后端接口。

**考虑过的替代方案**：

- **把任意 EOF 当成功**：违反 Turn 终态语义。
- **自动无限重连**：当前缺少完整重连预算和页面生命周期策略，属于独立可靠性功能。

## 决策 8：分层验证，不引入视觉测试依赖

**决策**：Gherkin 定义行为，Vitest/Testing Library 验证状态与可访问契约，Python 集成测试保护静态托管和公开接口，真实浏览器完成截图、溢出、焦点和 reduced-motion 验收。

**理由**：

- 单元 DOM 测试不能证明真实布局，截图也不能代替行为断言。
- 现有工具链已覆盖全部层次，无需仅为一次改版引入 Playwright。
- Vite 开发服务没有 `/api` 代理，最终端到端验收必须使用构建产物和 FastAPI 同源服务。

**考虑过的替代方案**：

- **只做截图比对**：无法验证任务创建、SSE、中断和安全配置。
- **只做组件测试**：无法发现真实浏览器中的遮挡、溢出和资源路径问题。
- **新增 Playwright**：当前没有持续视觉回归需求，不足以支持新依赖成本。
